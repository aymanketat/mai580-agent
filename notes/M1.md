# M1 — Graph foundations (Stages 1–5): progress note

**Use case B — Research Assistant** for machine-learning papers. **Repository:**
https://github.com/aymanketat/mai580-agent (private, `aniskoubaa` invited), tags `stage-01` … `stage-05`.
Model `gpt-4.1-mini`, temperature 0; langgraph 1.2.12, langchain 1.4.2, langchain-openai 1.6.6, Python 3.11.
Data: 23 arXiv records cached in `data/papers.json`; Semantic Scholar for citation counts (live).
Detailed report with every table and full reflection answers: `notes/M1_detailed.md`.

## What was built

| stage | graph | added |
|---|---|---|
| 1 | `START → model → END` | one `State` with `messages` + `add_messages` reducer; `call_model` node |
| 2 | `analyze → generate → review` | fields `analysis`, `draft`; three focused prompts (kept as `build_workflow()`) |
| 3 | `classify` → one of 5 answer nodes | structured-output classifier over `paper_lookup / literature_search / citation / concept / other`, conditional edge |
| 4 | router + `agent → tools → final_answer` | 3 read-only tools: `search_papers` (lexical, catalogue), `get_paper`, `format_citation` (APA/BibTeX/IEEE); errors returned as data |
| 5 | router + `agent ⇄ tools` | loop closed (`tools → agent`), `recursion_limit=12` with a polite fallback; `get_citation_count`, `check_citation` |

Tests: the suite at each tag passes 2 / 2 / 4 / 7 / 15 tests (re-run from checkouts of the tags;
`eval/results/test_runs.md`); the current tree passes 15. Tool tests run offline.

## Key results

**Stage 1 (5 research questions):** 2 correct, 2 honest refusals, 1 confident invention (VAE paper
"v10"; the catalogue says v11). Two separate runs of "My name is Sara" / "What is my name?" → no memory.

**Stage 2 vs Stage 1, same 10 questions** (3 blind LLM graders, median score 1–5):

| | latency | tokens in / out | quality | factual errors (contradict catalogue) |
|---|---|---|---|---|
| Stage 1, single node | 34.7 s | 307 / 4 330 | **3.9** | 2 answers |
| Stage 2, workflow | 66.4 s | 8 257 / 7 998 | **3.4** | 2 answers (+3 stale or unsupported additions) |

The reviewer node fixes tone and length, not facts: it hedged correct answers and passed "Llama 2
has 13 authors" (truth: 68); it helped only on the fake-reference check.

**Stage 3 routing** on 20 labelled requests: v1 descriptions 18/20 = 90% (both misses: reference
checks routed to `paper_lookup`); v2 wording 20/20 = 100% — tuned on the same 20 items, so an upper
bound until Stage 13's held-out set.

**Stage 4 vs Stage 5, 10 multi-step requests + 1 single-step control** (3 blind graders):

| measure | Stage 4: 1 round, 3 tools | Stage 5: loop, 5 tools |
|---|---|---|
| strict success (all parts done, citations/counts traceable to a tool call) | **0/10** | **6/10** |
| content-only success (hand-written citation counts if every field matches the catalogue) | 2/10 | 6/10 |
| single-step control | 1/1 | 1/1 |
| median score 1–5 (multi-step) | 2.10 | 4.00 |
| answers with a factual error | 2 | 0 |
| citations without tool provenance | 4 | 0 |
| tool calls · input tokens (multi-step) | 13 · 11 980 | 36 · 44 291 |
| loop-only subset: the 4 requests solvable with Stage 4's tools but needing two dependent calls | 0/4 strict (2/4 content-only) | 4/4 |

All four Stage 5 misses were Semantic Scholar rate limits, reported honestly ("could not retrieve");
with one retry added afterwards, three of them completed in a separate re-run.

## Main findings

- The model refuses when a question *announces* that it needs live or private data, and invents when
  the fact looks ordinary but lives in the long tail (version numbers, author counts, id → title).
- Adding steps without evidence (Stage 2) adds places to be wrong; adding tools (Stage 4) fixes the
  facts the catalogue holds; closing the loop (Stage 5) is what makes dependent calls possible.
- The loop costs 2.8× tool calls and 3.7× input tokens (every round re-sends history + schemas) and
  wastes calls (8 unnecessary in 11 requests): re-searching an id it already has, counting off-topic
  search hits. These motivate Stage 8 (retrieval quality) and Stage 9 (planning).

## Limitations

- Stage 4 → 5 changes the loop *and* adds two tools; 6 of the 10 multi-step requests need a new tool,
  so the comparison measures the combined upgrade. The 4-request subset above isolates the loop.
- The grader prompt wrongly said Stage 4 had five tools; success verdicts are unaffected, but some
  Stage 4 scores may be a point low and the claim counts were re-derived by hand. A re-grade with an
  explicit rubric changed no recorded score (`eval/results/stage05_regrade_q5_q8.json`).
- Flagged for review: CLIP counted as a "transformer for computer vision" (its abstract never says
  so; if off-topic, Stage 5 is 5/10); Q5's "most cited" cannot be audited because runs log tool
  calls, not tool results; Q9's "not authored by Yao" is false as written, arguably shorthand.

## Reflections (short; full answers in the detailed report)

A node returns an update and the reducer owns the merge; without `add_messages`, a node returning
`messages` would replace the history (nodes that return only `analysis` or `draft` leave it alone).
One edge, `tools → agent`, turns the workflow into an agent; `recursion_limit` is both a cost and a
safety control, but it counts steps, not money or risk. A structured-output classifier is safer than a
written label because the schema constrains the output.
